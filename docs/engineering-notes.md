# 개발 시 주의사항

## 2026-09-18 두 장짜리 배치는 배경 밝기를 사진마다 새로 정해야 한다

배경 기준을 232로 고정해 두면 안 된다. 어떤 사진은 배경이 246이고 카드 안의 흰 벽이 233이다. 고정 기준으로는 카드 내용을 배경으로 착각해 경계를 잘못 잡고, 결국 판정을 포기해 라운드를 건너뛴다(운영 검수 이미지 25장 중 11장이 그랬다). 배경은 밝은 쪽에서 가장 흔한 밝기로 정하고(`backgroundThreshold`), 그 값이 화면의 10%도 안 되면 두 장 배치로 보지 않는다.

경계는 두 번 잰다. 한 번만 재면 카드 안의 흰 소매 한 줄에 끌려가 카드가 실제보다 작게 잡히고, 마스크가 `dest-in`이라 작게 잡힌 만큼 카드가 지워진다. 1차로 맞닿은 쪽 끝 몇 줄을 보고 대강 잡은 뒤, 2차는 **그 카드만 있는 구간**의 줄을 모두 훑는다. 두 카드에 걸친 줄을 쓰면 배경이 나오지 않아 카드가 화면 끝까지 늘어난다.

마지막에 `uncoveredShare`로 상자가 못 덮은 카드 내용을 센다. 1%를 넘으면 깎지 않는다. 잘못 깎으면 그만큼 지워지므로, 안 깎는 쪽이 항상 안전하다.

기존 검수 이미지 보정(`repairAiPreviewCorners`)은 검은 모서리만 찾으면 안 된다. 두 장짜리는 모서리가 흰색이라 그냥 넘어간다. 두 장으로 읽히면 다시 깎는다.

검증: 원본 500장에 대해 한 장 469·두 장 28·판정 포기 3. 두 장으로 읽힌 사진을 마스크와 함께 렌더링해 카드가 지워지지 않고 네 모서리가 모두 깎이는 것을 눈으로 확인했다. 단위 테스트 11개.

## 2026-09-17 클립보드는 사람이 붙여넣을 때만 읽을 수 있다

브라우저는 스크립트가 `navigator.clipboard.readText()`로 클립보드를 읽는 것을 막는다(권한 없이는 거부). 렌즈 창에서 돌아올 때 자동으로 주소를 받아 오려던 방식은 동작하지 않았다. 대신 `paste` 이벤트를 받는다. 사람이 Ctrl+V를 누르는 순간에는 권한 없이도 내용을 읽을 수 있다.

구글렌즈에서 '링크 복사'를 하면 이미지 주소가 아니라 결과 페이지 주소가 나온다. 그 주소는 이미지가 아니므로 프록시가 422를 돌려주고 잘라내기 창은 아무것도 못 띄운다. '이미지 복사'로 그림 자체를 붙여넣으면 주소 없이 바로 자를 수 있다(`LensCardCropper`의 `local`). 붙여넣은 그림은 우리 쪽 blob이라 캔버스가 오염되지 않는다.

'먼저 처리'는 순서만 바꾸면 사람이 보기에 아무 일도 일어나지 않는다. 고른 만큼 바로 처리까지 시작하되, 이미 돌고 있는 작업이 있으면 그 작업이 우선순위 순서로 가져가므로 새 작업을 만들지 않는다.

## 2026-09-17 구글렌즈 후보는 카드 영역을 찍어 잘라내야 한다

주소만 받아 그대로 규격을 맞추면 안 된다. 구글렌즈로 찾은 사진에는 배경과 다른 물건이 함께 들어 있어 카드만 뽑아야 한다. 이미지 작업대가 쓰던 네 모서리 선택 계산(`detectCardBounds`·`seamlessQuadrilateralCrop`·`normalizeFourCorners`·`roundCanvasCorners`)을 `src/lib/card-crop.ts`로 옮겨 작업대와 AI 이미지 작업이 같은 계산을 쓴다. 화면(`LensCardCropper`)이 네 모서리를 받아 실제 카드 비율(54×86)로 잘라 보내고, 서버는 받은 그림을 `toRoundedCardJpeg`로 마무리한다.

다른 도메인 이미지는 캔버스를 오염시켜 `toDataURL`이 막힌다. 후보 이미지는 반드시 `GET /api/products/<id>/image-workbench?url=…` 프록시로 불러온다. 이 경로에는 내부망 차단(`assertSafeRemoteUrl`)이 걸려 있다.

되돌리기: `ai_image_jobs.backup_preview_url`에 사람이 손대기 전의 AI 결과를 한 번만 보관한다. 렌즈 결과를 연달아 바꿔도 되돌릴 대상은 언제나 AI가 만든 결과다. 되돌리면 보관본을 비워 같은 작업을 두 번 되돌리지 않는다.

먼저 처리: `ai_image_jobs.priority`가 크면 먼저 처리한다. 대기 작업 선택과 처리 예정 목록 모두 `priority DESC → created_at → sku` 순서를 쓴다. 제외한 상품을 먼저 처리로 고르면 대기열로 되돌린다. 순서 기준을 한 곳만 바꾸면 화면과 실제 처리가 어긋나므로 두 질의를 함께 고친다.

검증: 단위 테스트 10개(잘라낸 이미지 저장·내부망 차단·확정 작업 거부·되돌리기·보관본 없음·우선순위 SQL·순서 기준 2곳). 배포 후 운영에서 우선 처리(461443이 맨 앞으로), 잘라낸 이미지 저장 → 되돌리기 → 연속 되돌리기 거부까지 확인했다. 704개 테스트·lint 오류 0·빌드 통과. dpl_q1CmNkvPHUimjrSfuYsc7cXZYNtm.

사람이 준 주소를 서버가 대신 내려받는 경로에는 반드시 내부망 차단을 건다. 기존 작업대 라우트에만 있던 검사를 `assertSafeRemoteUrl`로 꺼내 두 곳이 같은 규칙을 쓴다.

## 2026-09-17 카드 두 장이 담긴 사진의 모서리 처리

처리 예정 344건을 훑어 16건(약 5%)이 한 사진에 카드 두 장을 대각선으로 담고 있었다(왼쪽 위·오른쪽 아래). 앞뒤 한 장인 경우와 서로 다른 두 멤버인 경우가 섞여 있다. 지금까지는 프레임 전체를 한 장으로 보고 바깥 네 모서리만 깎아, 맞닿은 두 모서리만 잘리고 나머지는 각진 채로 남았다. 뒷면이 검은 카드일 때는 잘린 자리에 흰 부채꼴이 보였다.

`detectCardLayout`이 배치를 먼저 가린다. 네 귀퉁이의 밝기를 보고 오른쪽 위·왼쪽 아래가 배경이면서 왼쪽 위·오른쪽 아래에 내용이 있으면 대각선 두 장으로 본다(반대 방향도 지원). 사분면 밝기로는 가릴 수 없다. 두 카드가 가운데에서 맞닿아 서로의 사분면을 침범하기 때문이다. 경계는 첫 줄·첫 열·마지막 줄·마지막 열을 훑어 내용이 끝나는 지점으로 잡고, 카드로 보기 어려운 크기·비율이면 `unknown`으로 두어 아무것도 깎지 않는다. 비율 판정은 정규화 좌표를 그대로 나누지 말고 화면 비율을 곱해 실제 모양으로 해야 한다.

한 장짜리는 판정이 `single`로 떨어져 기존 동작(바깥 테두리 반경 4.5%)이 그대로다. 실제 표본으로 확인했다. 두 장인 경우 카드마다 자기 짧은 변의 4.5%를 반경으로 쓴다.

검증: 합성 이미지 9개 테스트(대각선 양방향·꽉 찬 한 장·여백 있는 한 장·너무 좁은 상대 카드·귀퉁이 표식·마스크 생성)와 실제 포카마켓 사진 4장으로 확인했다. 694개 테스트·lint 오류 0·빌드 통과. dpl_GEYoTyVGcCiEWtcGHEmpQYJ7cXjC.

## 2026-09-17 등록 가능한 전체 등록 버튼

`POST /api/products/publish`는 이미 `allEligible`을 받고 있었고 화면만 개수를 입력해 받는 방식이었다. 재고관리 신규등록에 `등록 가능한 전체 등록` 버튼을 추가했다. 누르면 채널별 등록 가능 수와 제외 사유(미등록 후보 중 기존 연결·가격 미입력)를 먼저 조회해 보여 주고, 사람이 확인해야 접수한다.

대상 목록을 화면에서 만들어 보내지 않고 `allEligible`로 접수한다. 서버가 접수 시점에 같은 조건으로 다시 고르므로, 조회와 접수 사이에 등록된 상품을 중복해서 보내지 않는다. 한 번에 채널당 500개(요청 스키마 상한)까지 접수하고 응답의 `remainingProductCount`를 화면 문구로 알려 다시 누르게 한다. 자동으로 이어서 접수하지는 않는다. 실제 판매 등록은 사람이 누를 때만 시작해야 한다.

## 2026-09-17 변동작업이 계속 실패하던 세 가지 원인

최근 작업 10건의 실패를 원인별로 모으니 세 갈래였다.

**1. eBay 이미지 50건 — 검증 방법이 틀렸다.** eBay는 URL로 받은 사진을 자기 서버(i.ebayimg.com)로 복사하고, GetItem에서 원본 주소(`ExtendedPictureDetails.ExternalPictureURL`)를 아예 돌려주지 않는 리스팅이 있다(`DetailLevel=ReturnAll`을 붙여도 비어 있다). 그런데 확인 코드는 우리가 보낸 주소가 응답에 들어 있어야만 성공으로 인정했다. 실제로는 반영이 끝났는데 매번 실패로 남았다. 확인 수단을 `verifyEbayPictures`로 나눴다. ① Inventory API로 주소를 그대로 대조했으면 그것이 가장 정확하고 ② GetItem이 원본 주소를 주면 그 주소로 확인하고 ③ 원본 주소를 하나도 주지 않으면 사진 개수 일치까지만 확인한다. 어떤 방법으로 확인했는지 동기화 로그에 남기며, 개수만 맞춘 확인을 "구매자 화면까지 확인"으로 읽으면 안 된다. 실패했던 57건을 다시 실행해 성공 54·실패 0(종료된 리스팅 3건 제외)으로 정리했고, 로그에는 모두 `검증 완료(inventory)`로 남았다.

**2. Shopify 옵션 삭제 5건 — 죽은 연결을 계속 붙잡고 있었다.** 별도 항목으로 정리했다. 82794·82797·82800·82811에 이어 17506도 같은 상태였고, 이 때문에 3136의 묶음 이미지 교체가 "저장된 전체 옵션과 Shopify 옵션이 일치하지 않아" 중단됐다. 오류 메시지에 저장 개수·Shopify 개수·없는 상품번호를 넣어 무엇이 어긋났는지 바로 보이게 했다. 17506의 연결을 정리한 뒤 3136 묶음 이미지는 성공했다.

**3. 반영 대상이 아닌 건이 실패로 쌓였다.** 게시 대기(`publication_pending`) 상태이거나 채널 연결이 없는 상품에 이미지 작업을 걸면 "이미지를 반영할 채널 연결이 없습니다"로 실패했다. 고칠 수 없는 상태를 실패로 쌓으면 목록이 계속 붉게 남는다. 이제 `AlreadyRegistered`로 건너뛰고 무엇이 먼저인지 알려 준다("게시할 때 이미지가 함께 반영됩니다" / "신규등록이 먼저입니다").

실패 원인을 감싸 버리면 화면에는 "재시도가 필요합니다"만 남는다. 외부 채널 작업에서 오류를 다시 던질 때는 원인 문자열을 반드시 보존하고, 확인 방법이 채널마다 다르면 그 방법 자체를 로그에 남긴다.

## 2026-09-17 변동처리 실패 원인이 화면에 남지 않던 문제

후속: 반영과 보류가 모두 실패하면 옵션이 실제로 삭제됐는지 확인한다. 옵션 조회가 GraphQL 오류 없이 비어 있고 상위 상품 조회까지 정상 응답해야 삭제로 본다(확인 질의 자체가 실패하면 삭제로 단정하지 않고 원래 실패를 알린다). 삭제가 확인되면 `shopify_product_id`·`shopify_variant_id`·`shopify_inventory_item_id`·`shopify_status`를 비우고 "연결을 해제했습니다. 신규등록으로 다시 올려 주세요"로 알린다. 연결이 없는 상품은 변동처리 작업자가 `uploadProductToShopify`로 새로 등록하므로 다음 실행에서 자동으로 복구된다.

기존 검사 "보류 요청도 실패하면 판매 차단 완료로 표시하지 않는다"는 쓰기 요청이 없어야 한다는 뜻이었다. 읽기 전용 확인 질의는 허용하되 mutation이나 재고 쓰기가 섞이지 않는지 검사하도록 바꿨다. 실패 경로에 새 호출을 넣을 때는 그 호출이 읽기인지 쓰기인지 테스트로 못 박는다.

Shopify 가격·수량 반영이 실패하면 `syncShopifyPriceAndInventory`가 보류(수량 0)를 시도하고, 그마저 실패하면 원래 오류를 버리고 "판매 보류 미확인 상태이며 재시도가 필요합니다"만 던졌다. 화면에는 재시도하라는 말만 남아 무엇을 고쳐야 할지 알 수 없었다. 이제 반영 실패 원인과 보류 실패 원인을 함께 담는다. 실패를 감싸 버리는 곳에서는 원인 문자열을 반드시 보존한다.

원인 대조는 `POST /api/admin/shopify-link-check`로 한다(읽기 전용). 저장된 `shopify_product_id`·`shopify_variant_id`·`shopify_inventory_item_id`와 Shopify가 실제로 돌려주는 값을 나란히 보여주고, 옵션이 없으면 상위 상품과 같은 상품번호의 다른 옵션까지 조회한다. 옵션 조회가 GraphQL 오류 없이 null이고 상위 상품 조회는 성공하면, 권한·통신 문제가 아니라 옵션이 실제로 삭제된 것이다. 이 구분 없이 연결을 지우면 일시적인 오류에도 판매 연결을 잃는다.

## 2026-09-17 통과한 카드가 나타났다 사라졌다 하던 문제

자동 처리 중에는 배치 진행에 맞춰 목록을 다시 받아온다. 목록 요청이 여러 개 겹치면 처리 이전 시점의 응답이 나중에 도착할 수 있고, 그 응답에는 방금 통과시킨 카드가 아직 `review`로 들어 있다. 어제 넣은 판정 유지 장치는 "목록에 없으면 판정을 지운다"고 되어 있어, 처리 후 목록(카드가 빠진 상태)이 먼저 도착하면 판정이 지워지고, 뒤이어 도착한 옛 응답이 카드를 되살렸다. 그래서 나타났다 사라졌다를 반복했다.

판정 기록은 화면을 여는 동안 지우지 않는다. 목록에 없다는 이유로 지우면 늦게 도착한 응답을 막을 수 없다. 서버가 다른 상태로 반영하면 그 상태를 그대로 쓰되 기록은 남긴다. 추가로 판정을 보내는 동안에는 배치 진행에 따른 자동 새로고침을 멈춘다(`decidingRef`).

같이 확인한 것: 통과했지만 업로드되지 않은 37건이 남아 있었다. 결과 이미지 생성 시각이 모두 2026-09-16 06:06~06:26 UTC로, 업로드 한 건에 5~13초가 걸리고 라우트에 실행 시간 설정이 없던 시기의 잔재였다. 지금 경로는 한 건에 1.3초이며 37건을 모두 올려 성공 37·실패 0으로 정리했다. 리전을 맞춘 뒤 `approveAiJob`의 R2 복사도 정상 동작한다.

## 2026-09-17 앱 전체가 느리던 진짜 원인: 함수와 데이터베이스가 다른 대륙

| | 이전 | 이후 |
| --- | --- | --- |
| DB 왕복(SELECT 1) | 705~7,900ms | 7~8ms |
| 주문 목록(전체) | 2.2초 | 0.38초 |

브라우저에서 서버까지는 한국 기준 150ms 정도 멀어지지만, 화면 한 번에 사라지는 DB 왕복이 10여 번이라 비교가 되지 않는다. 포카마켓 동기화는 시드니에서도 정상 진행하며(45초에 2건, 속도는 API 대기 시간이 결정한다) 배경 부하가 원인이 아니었다.

## 2026-09-16 등록 이미지 캐시 키에서 묶음 썸네일 설정 제외

`products/channel-watermarked` 키는 렌더 버전·원본 주소·로고·배경 적용 여부·설정 JSON 전체의 해시였다. 설정 JSON에는 등록 이미지 렌더가 읽지 않는 묶음 썸네일 전용 값(`variationWatermarkOpacity`·`variationWatermarkLogoSize`·`variationWatermarkGap`)도 들어 있어서, 묶음 썸네일 워터마크만 조정해도 등록 이미지 2,200여 장이 전량 새로 만들어지고 이전 세대가 R2에 그대로 남았다. 이제 `listingImageRenderSignature`로 렌더가 실제로 읽는 24개 값만 해시한다. 묶음 썸네일은 `products/variation-thumbnails`의 자기 키를 쓰므로 영향이 없다.

## 2026-09-16 재처리로 지운 검수 결과 복구와 대기 순서 고정

`기존 검수 결과 개선 재처리`는 확인 절차 없이 검수·보류·통과 결과를 대기열로 되돌리고 `preview_url`을 비웠다. 잘못 눌러 4장(505133~505136)의 결과 주소가 사라졌지만, R2 객체는 지워지지 않으므로 복구할 수 있었다. 재처리 SQL이 `processed_at`은 지우지 않기 때문에 밀리초 단위 시각이 남고, 키는 `ai-image-reviews/<sku>/<Date.now()>-dewatermark.jpg` 형식이며 관측상 키 시각은 `processed_at`보다 495~1,793ms 앞섰다. 그 구간을 HEAD로 훑어 네 장을 모두 찾았고, `claim` → `complete`(기존 엔드포인트)로 같은 이미지를 다시 올려 검수 대기로 되돌렸다. 크레딧은 쓰지 않았다.

검증: 실제 Postgres(PGlite)에서 동시각 작업이 SKU 순서로, 더 먼저 담긴 작업이 앞서 선택되고 BTS는 제외되는 것을 확인했다. 642개 테스트·lint 오류 0·빌드 통과. 배포 후 운영에서 복구된 4장이 검수 대기(540×860·흰 모서리)로 보이고 처리 예정은 4,205건임을 확인했다.

## 2026-09-15 둥근 모서리가 검게 남던 AI 결과 이미지

모서리 색을 흰색으로 둘지 투명 PNG로 둘지 실제 렌더러로 측정했다. 등록 이미지는 업로드 단계 `createPreparedListingImage`가 원본을 4.5% 반경(540×860이면 24px)으로 **다시** 라운드 처리한 뒤 배경 캔버스에 올리고 마지막에 JPEG로 저장한다. 즉 AI 단계의 라운드는 최종 모양이 아니다. 배경 이미지를 쓰는 실제 설정으로 비교하면 흰 모서리 JPEG 결과에 남는 흰 화소는 0개이고, 투명 PNG를 넣었을 때와의 차이는 96만 화소 중 396개(0.04%, 모서리마다 1px 호)였다. AI 단계 라운드를 아예 빼도 282개는 남는다(투명 알파 경계와 불투명 경계의 차이). 반면 실제 카드 1장 기준 용량은 JPEG 45KB, 투명 PNG 630KB로 14배이며 전체 16,738장 기준 0.73GB 대 10.05GB다. 따라서 중간 저장은 흰 배경 JPEG를 유지하고, AI 단계 반경만 업로드 단계와 같은 `listingImageCornerRadius` 공식으로 맞춘다(25px 고정값 제거). 반경이 다르면 검수에서 본 모서리와 등록 이미지의 모서리가 어긋난다.

sharp는 한 파이프라인 안에서 `flatten`을 `composite`보다 먼저 적용한다. `resize → composite(dest-in 라운드 마스크) → flatten({background:'white'}) → jpeg` 순서로 호출해도 흰 배경은 마스크 이전 상태에 적용되므로, 잘려나간 모서리는 알파만 0이 되고 JPEG에는 알파가 없어 그 자리가 검은색(0,0,0)으로 남는다. 입력에 알파가 있든 없든(`raw` RGBA, JPEG, `ensureAlpha` 모두) 결과는 같다. 라운드 결과를 PNG로 확정한 뒤 두 번째 파이프라인에서 흰 배경을 깔아야 한다(`toRoundedCardJpeg`). 수동 등록 이미지 경로 `createPreparedListingImage`는 원래부터 라운드 PNG를 만든 뒤 캔버스에 합성하므로 영향이 없다.

검수 화면에서 검게 보이는 모서리는 투명이 아니다. JPEG에는 투명이 없으므로 투명으로 남길 수 없고, 등록 이미지 규칙대로 흰색이어야 한다.

영향 범위: `-dewatermark.jpg` 키로 저장된 2026-08-03·09-15 결과 33장이 검정, 2026-07월 로컬 작업자 결과 94장은 흰색이었다. 전체 상품 16,738개 전수 확인 결과 AI 승인 경로(`products/<sku>/<sku>.jpg`)로 올라간 상품 이미지는 0개여서 판매채널에 나간 이미지에는 영향이 없었다.

복구: `repairAiPreviewCorners`는 Dewatermark 크레딧 없이 기존 검수·보류·업로드 대기 이미지를 내려받아 모서리가 어두울 때만 같은 마스크를 다시 씌워 흰 배경으로 다시 올린다. 카드 그림은 바뀌지 않으며 이미 흰 모서리면 건너뛴다. `created_at` 순서와 상태는 그대로 두어 검수 순서를 흔들지 않는다.

검증: 실제 7월 결과물에 현재 코드를 적용하면 모서리가 0,0,0, 2패스 수정안은 255,255,255이고 중앙 화소는 동일함을 확인했다. 632개 테스트(모서리 회귀 3개 포함)·lint 오류 0·빌드 통과. dpl_J5otbMvX11i4833pp3UpHLcGzsgz 배포 후 운영에서 127장 전수 보정(수정 33·정상 94·실패 0)했고, 재검사에서 127장 모두 흰 모서리를 확인했다.
