# 개발 시 주의사항

## 한글이 깨져 보이는 파일

증상: 일부 기존 문서와 소스의 한글 문자열이 `?` 또는 잘못된 문자로 보인다. 원인: 과거 파일이 서로 다른 문자 인코딩으로 저장되었거나 이미 손상된 상태다. 대응: 의미를 추측해 일괄 치환하지 말고 화면·테스트·사용자 확인으로 원문을 복원한다. 변경 뒤 실제 브라우저와 `rg` 결과에서 깨진 문자열이 새로 늘지 않았는지 확인한다.

## Windows 경로와 빌드

증상: 기본 빌드 도구가 한글이 포함된 Windows 경로에서 실패하거나 멈출 수 있다. 원인: 이 프로젝트는 해당 문제 때문에 개발·빌드 명령을 webpack으로 고정했다. 대응: `package.json`의 `--webpack`을 임의로 제거하지 말고, 도구 변경 전 같은 경로에서 `npm run build`를 완료해 검증한다.

## 요청 중 데이터 구조 생성

증상: 일부 AI 이미지·포카마켓 기능은 첫 요청 때 테이블과 인덱스를 만든다. 원인: 정식 마이그레이션에 완전히 편입되지 않은 기능이 현재 작업 상태에 포함돼 있다. 대응: 관련 데이터 구조를 바꿀 때 런타임 생성 SQL과 실제 데이터베이스를 모두 조사하고, 정식 마이그레이션으로 옮긴 후 반복 호출과 기존 데이터 보존을 확인한다.

## 외부 이미지 캐시

증상: R2 이미지를 교체해도 이전 사진이 계속 보일 수 있다. 원인: 공개 URL과 CDN·브라우저 캐시가 같은 키의 이전 응답을 유지한다. 대응: 이미지 교체는 새 객체 키 또는 명시된 캐시 무효화 흐름을 사용하고, 원본·프록시·브라우저에서 실제 새 이미지가 보이는지 확인한다.

## 포카마켓 휴대전화 자동화

증상: 화면 문구, 좌표, 결제 단계가 조금만 바뀌어도 작업이 실패하거나 잘못된 위치를 누를 수 있다. 원인: 현재 연결은 Android 화면 구조와 좌표에 의존한다. 대응: 가격 상한과 현재 화면 문구를 매 단계 다시 확인하고, 결제 인증은 사람에게 넘긴다. 실패 시 무한 재시도하거나 다른 버튼을 추측해 누르지 않는다.

## 이미지 품질 확인

워터마크 제거 개선은 평균 점수만으로 판단하지 않는다. 글자 잔상, 카드 무늬 훼손, 테두리 변형, 앞·뒤 이미지 뒤바뀜 사례를 고정 검증 세트로 유지하고, 기존 승인 이미지와 나란히 사람이 확인한다.

## eBay 가격·재고 대량 반영

소량 자동화의 `ReviseInventoryStatus` 직접 호출은 요청당 최대 4개와 동시성 3을 지킨다. 운영 화면의 대량 가격·재고 반영은 상품별 `GetItem` 재조회로 완료를 기다리지 않고 공식 `LMS_REVISE_INVENTORY_STATUS` Sell Feed 파일 하나로 최대 2,000건을 제출한다. eBay task ID와 상품별 MessageID를 작업에 저장하고 결과 파일의 CorrelationID별 Success/Error로 완료를 확정한다. 단품은 Item ID만, 묶음 옵션은 Item ID와 SKU를 함께 보낸다. 외부 성공 뒤 내부 `ProductListing` 기록을 여러 `Promise.all` 쿼리로 실행하면 연결 제한 1인 운영 DB에서 pool timeout이 날 수 있으므로 100개 이하 트랜잭션 묶음으로 순차 저장한다. 브라우저 요청 수명에 작업을 묶지 말고 영구 작업과 task ID를 먼저 남겨 메뉴 이동·중단·재개에 안전하게 한다.
## Shopify 운영 배치에서 전체 목록을 상태 조회로 사용하지 않는다

- `getShopifyOperations()`는 이미지 준비 상태, 옵션 묶음, 예약 재고, 가격과 기존 채널 연결을 함께 계산하는 무거운 조회다.
- 작업 상태를 몇 초마다 확인하거나 각 상품 처리 전후에 이 함수를 호출하면 서버리스 요청이 겹쳐 `connection_limit=1` 환경에서 P2024와 300초 타임아웃이 연쇄적으로 발생한다.
- 자동검증에서 확정한 대상은 서명된 스냅샷으로 작업 큐에 넘기고, 진행 화면은 작업 테이블만 읽는 전용 API를 사용한다. 전체 운영 목록은 배치 완료 후 한 번만 다시 계산한다.
- 작업 가져오기는 짧은 DB advisory lock 안에서만 수행하고 Shopify 네트워크 호출 중에는 DB lock이나 트랜잭션을 유지하지 않는다.
- 묶음상품 옵션 재고는 옵션별 REST 쓰기·재조회를 반복하지 않는다. `inventorySetQuantities`로 절대수량을 한 번에 설정한 뒤 `inventory_levels`를 한 번에 재조회하고, 실제값이 다른 옵션만 실패로 남긴다.
- 신규등록 작업이 서버 제한시간을 넘기면 바로 재등록하지 않는다. Shopify의 옵션 SKU를 먼저 검색해 완전한 동일 묶음이 있으면 외부 ID를 복구한 뒤 기존 상품 수정으로 재개하고, 아무 SKU도 없을 때만 신규등록을 다시 시작한다. 일부 SKU만 있거나 여러 상품으로 갈라진 경우는 자동 재시작하지 않는다.
- GraphQL 실패 로그에는 액세스 토큰이나 변수를 남기지 말고 operation 이름과 요청 길이만 남긴다. 429·5xx·`THROTTLED` 같은 일시 오류만 짧게 재시도하며 문법·검증 오류는 즉시 해당 항목 실패로 확정해 다음 작업을 막지 않는다.
- 판매용 개별 워터마크 이미지는 원본 URL과 워터마크 설정 서명으로 만든 결정적 R2 키를 사용한다. 같은 키가 이미 있으면 원본 다운로드·Sharp 렌더링·R2 업로드를 반복하지 않고 기존 공개 URL을 재사용한다. 개별 워터마크가 꺼져 있으면 원본을 다운로드하지 말고 승인 이미지 URL을 그대로 사용한다.
- Shopify 묶음상품 REST 생성 본문에는 사진을 함께 넣지 않는다. source marker가 없는 사진을 먼저 만들었다가 `productCreateMedia` 사진으로 교체하면 같은 사진을 두 번 수집하게 된다. 상품·옵션을 만든 뒤 관리 이미지 경로로 한 번만 업로드하고 옵션별 미디어 연결을 검증한다.
