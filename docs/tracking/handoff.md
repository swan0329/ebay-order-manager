# 통합관리 인수인계

eBay 한 곳으로 만들어진 시스템에 Shopify를 붙여 주문과 재고를 한 곳에서 관리하는 중이다.
이 문서는 어디까지 됐고 무엇이 남았는지, 그리고 다시 조사하지 않아도 되는 확인된 사실을 담는다.

기준 커밋: `ca0eefb`

## 지금 상태

| 영역 | 상태 |
| --- | --- |
| 주문 수집 | eBay·Shopify 모두 API로 들어온다. 다만 사람이 버튼을 눌러야 한다. |
| 재고 | 채널과 무관한 단일 원장. 주문이 들어오면 즉시 예약으로 잡힌다. |
| eBay 가격·수량 | API로 바꾼다(`ReviseInventoryStatus`). 미리보기 → 사람 확인 → 전송. |
| eBay 신규 등록 | 아직 CSV. 작업 4번에서 API로 옮긴다. |
| Shopify 상품 | API로 등록하고 재고를 맞춘다. SKU가 들어가므로 주문 매칭이 정확하다. |
| 클레임(취소·반품) | 없다. 취소돼도 재고가 돌아오지 않는다. |

## 확인된 사실 · 다시 조사하지 않는다

운영 API와 데이터베이스로 직접 확인한 값이다.

- eBay `sell.fulfillment`(주문·배송) 한도는 하루 100,000건이고 아직 쓰지 않았다. 10분 주기로 주문을 받아도 0.14%다.
- eBay `sell.inventory`(재고 변경) 한도는 하루 2,000,000건이다. 한도는 제약이 아니다.
- eBay `developer.analytics`(사용량 조회) 한도는 하루 5,000건이다. 사용량을 보는 일 자체가 이 한도를 쓰므로 화면은 30분마다만 확인한다.
- 계정 정지 사유로 알려진 것은 정책 위반, 거래 불량률 2% 초과, 판매자 실적, 수수료 미납이다. **호출량은 목록에 없다.**
- 실제 판매 제한 사례는 **재고 없음으로 주문을 취소한 것이 쌓인 경우**다. 재고를 채널에 반영하지 **않는** 쪽이 위험하다.
- Shopify 토큰은 24시간 뒤 만료된다. 자격 증명으로 그때그때 발급받아 쓰고, 만료 전에 다시 받는다.
- Shopify에서 `write_orders`는 `read_orders`를 포함한다. 권한 목록에 read가 안 보여도 정상이다.

## 반드시 지킬 것

### eBay 신규 등록을 API로 해도 된다. 두 가지를 코드가 막아야 한다

"API로 등록해서 계정이 정지됐다"는 사례는 찾지 못했다. eBay는 공식 API로 서드파티 등록 도구를
지원하고 `AddItem` 한도도 하루 100,000건이다. 위험한 것은 API가 아니라 **API로 만든 결과물**이다.
사람이 파일을 검토하던 단계가 사라지므로 그 검토를 코드가 대신해야 한다.

- **중복 리스팅** — 같은 카드를 두 리스팅으로 올리면 정책 위반이다. 등록 전에 그 카드가 이미
  활성 리스팅에 있는지 확인한다. 다만 그룹·앨범·멤버·상품명이 모두 같아도 **포즈가 다르면 다른
  카드**다. 이미지 지문(`image_phash`)이 다르면 별개로 본다.
- **월 판매 한도** — 넘겨서 만든 리스팅은 eBay가 끝내 버린다. 남은 한도보다 많이 만들지 않는다.

### 되돌리기 어려운 변경은 사람 확인을 거친다

재고 일괄 수정, 상품 병합·삭제, eBay 쓰기는 먼저 무엇이 바뀌는지 보여 주고 사람이 확인한 뒤에만
실행한다. `dryRun` 옵션을 먼저 만들고 화면은 미리보기를 반드시 거치게 한다.
가격·수량 반영(`ca0eefb`)이 그 본보기다. 근거는 `docs/tracking/decisions/0001-human-confirmation.md`.

### 재고 숫자를 추측으로 만들지 않는다

예약 수량은 열에 저장하지 않고 주문에서 계산한다(`src/lib/stock-reservation.ts`). 저장하면 차감·취소·
연결 변경 때마다 맞춰야 하고 한 번 어긋나면 아무도 모른다. 같은 이유로 가격도 정할 수 없으면
비워 두지 지어내지 않는다.

### 작업은 별도 워크트리에서, 배포는 명령으로

작업 폴더는 `main`보다 뒤처져 있고 미커밋 파일이 많다. 거기서 작업하거나 배포하면 최신 코드가
사라진다. GitHub에 올리는 것만으로는 배포되지 않는다.

```
git worktree add ../work-<name> -b feat/<name> origin/main
# 작업 → npx tsc --noEmit → npx eslint → npx vitest run → npm run build
git push origin feat/<name>:main
npx vercel deploy --prod --scope tngks2313-9711s-projects
```

## 남은 작업 · 권장 순서

### 1. 주문 자동 수집

사람 손 없이 주기적으로 주문이 들어오게 한다. `vercel.json`에 cron을 더하고
`/api/cron/orders-sync`를 만들어 기존 `/api/orders/sync`와 `syncShopifyOrders()`를 부른다.
`CRON_SECRET` 검사는 `/api/cron/pocamarket-sync`를 그대로 따른다.
주기는 30분으로 시작한다. Shopify는 `updated_at_min`으로 바뀐 주문만 받으므로 마지막 성공 시각을
저장해야 한다.

### 2. 재고 변경 시 채널 자동 반영

이미 있는 `syncShopifyInventory()`와 `pushEbayInventory()`를 재고 이력 생성 지점
(`createInventoryMovement`)과 주문 차감 뒤에 연결한다. 요청 안에서 동기로 부르면 느려지므로
`after()`로 응답 뒤에 돌리고, 실패해도 재고 변경 자체는 살린다.
올리는 수량은 반드시 `sellableQuantity()`를 쓴다. 실재고를 올리면 이미 팔린 카드가 또 팔린다.

### 3. 클레임 수집과 재고 복구

취소·반품·환불이 들어오면 재고를 되돌린다. eBay `post-order` API와 Shopify 주문의 `refunds`,
`cancelled_at`을 읽는다. 복구는 `CANCEL_RESTORE` 이력으로 남긴다.
같은 취소로 두 번 복구하면 안 된다. 재고 차감이 `stockDeducted`로 중복을 막는 방식을 따른다.

### 4. eBay 신규 등록 API

`AddFixedPriceItem`(옵션상품은 Variations 포함) 또는 Sell Inventory API를 쓴다.
기존 CSV 생성 로직(`/api/export/ebay-listings`, `listing-upload/variation-groups/export`)이 제목,
설명, item specifics, 가격을 이미 만들고 있으므로 **같은 값을 보내면 된다**. 가격은 반드시
`src/lib/listing-price.ts`를 쓴다.

먼저 `VerifyAddFixedPriceItem`으로 검증만 해 보고 통과하면 실제 등록한다. 첫 실행은 한두 개만 한다.
위의 "반드시 지킬 것"에 적은 중복 검사와 잔여 한도 확인, 미리보기를 함께 넣는다.
등록 뒤에는 `ebay_item_id`와 `listing_status`를 저장한다.

### 5. Shopify 송장 전송

배송 처리하면 Shopify에도 송장이 올라가게 한다. 기존 `/api/orders/[id]/fulfillments`가 주문의
`channel` 값을 보고 갈라지게 한다. eBay 전용 코드가 Shopify 주문에 닿으면 `ebayOrderId`가 비어 있어
실패한다.

### 6. ProductListing 표로 채널 추상화

`ProductListing { productId, channel, externalId, price, quantity, status }`를 만들고 `Product`의
eBay 열 열네 개와 Shopify 열 세 개를 그리로 옮긴다. 기존 열을 지우지 말고 새 표를 채운 뒤 읽는
쪽을 하나씩 옮긴다. 주문 채널화(`50febaf`)가 그 방식의 본보기다.

### 7. 자동화 규칙

"재고가 0이면 리스팅 종료" 같은 규칙을 설정으로 둔다. 규칙이 돈과 리스팅을 건드리므로 기본은
알림만 하고 자동 실행은 사람이 켤 때만 한다.

### 8. 정산 대조

마진 계산값과 eBay·Shopify 실제 정산액을 대조한다. eBay `sell.finances`, Shopify Payouts를 읽는다.
읽기만 하므로 위험이 없다.

## 밟았던 함정

- **같은 이름이 같은 카드가 아니다.** 포즈만 다른 카드가 한 이름에 열네 장까지 있다. 중복으로 보고
  병합하려다 되돌렸다(`39dda09` → `5d1c416`).
- **주문 SKU가 비어 온다.** 옛 리스팅에 Custom Label이 없어서다. 그럴 때 제목 유사도로 가면 이름만
  같은 다른 포즈에 붙는다. `products.ebay_item_id`를 먼저 본다(`351fb9b`).
- **포카마켓 기준가는 빠른구매 최저가다.** 1:1 거래가가 아니다. 같은 카드라도 두세 배 차이 난다.
- **기존 기능을 먼저 찾는다.** 일괄 업로드가 이미 있는데 새로 만들었다가 지웠다.
- **운영 데이터를 봐야 하면 임시 진단 경로를 쓴다.** `DIAG_SECRET`으로 보호한 라우트를 잠깐 올리고
  확인 뒤 반드시 지운다. 자격 증명을 밖으로 옮기지 않는다.

## 사람이 판단할 일

### 2026-08-20 Codex 구현 후 운영 확인

- 1~3, 5~8번 코드와 운영 배포를 완료했다. 4번 신규 등록도 미리보기·중복 차단·잔여 한도·최대 2개 제한까지 구현했지만 실제 게시하지 않았다.
- 신규등록의 Seller Hub 잔여 한도 수동 입력은 2026-08-20 사용자 요청으로 제거했다. 대신 한 번에 최대 50개, 중복·필수값 미리보기, 15분 확인 토큰을 유지한다.
- 정산 대조를 사용하려면 eBay를 `sell.finances` 포함 권한으로 다시 연결하고 Shopify 앱에 `read_shopify_payments_payouts`를 추가해야 한다.
- 자동화 규칙은 기본 `알림만`이다. 자동 종료는 재입고 시 자동 재등록되지 않으므로 관리자가 미리보기 후 필요할 때만 켠다.
- 재고 1 실판매 후 eBay와 Shopify 수량이 0이 되는지 실제 채널 화면에서 확인하는 운영 검증은 여전히 필요하다.

- 포카마켓 전체 최신화가 진행 중이다. 끝나면 판매가를 eBay에 반영해야 한다. 그전까지 저가 판매가 이어진다.
- 리스팅 `157910130906`에서 주문이 세 건인데 재고는 한 장이었다. 실물 확인 후 취소·환불이나 재고 수정이 필요하다.
- eBay 가격·수량 API 반영과 Shopify 주문 가져오기는 **실제 건으로 검증하지 않았다.**
- 작업 폴더의 미커밋 파일을 무엇을 남기고 무엇을 버릴지 정해야 한다. `backup/worktree-20260820`에 현재 위치를 표시해 두었다.
