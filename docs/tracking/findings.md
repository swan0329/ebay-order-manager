## Shopify 옵션상품 등록 미구현

2026-08-31 확인 결과 eBay는 그룹·앨범·버전이 같은 카드를 옵션상품으로 신규 구성하고, 이미 확정된 부모 Item ID가 있으면 포함되지 않은 카드만 새 옵션으로 추가한다. 일반 eBay 개별등록 CSV와 재고 Draft는 옵션 후보를 제외하도록 보강했다. 반면 Shopify 등록은 현재 각 SKU를 `Default Title` 단일 옵션 상품으로 생성하며 기존 Shopify 상품에 새 variant를 묶어 넣는 상태·업로드 경로가 없다. 중복 개별 상품 생성을 막기 위해 옵션 후보의 신규 Shopify 개별·다건 등록을 차단했다. Shopify에서도 옵션 우선 등록을 제공하려면 그룹별 부모 Product ID와 포함 variant를 저장하고, 기존 variant를 보존하면서 신규 variant만 추가하는 GraphQL 작업 및 결과 검증을 구현해야 한다.

## Shopify Client Secret 교체 필요

2026-08-31 로컬의 미추적 `scripts/shopify-exchange-token.mjs`에서 Shopify Client Secret 하드코딩을 발견해 환경변수 전용으로 수정했다. git 추적 파일은 아니지만 과거 Vercel CLI 배포가 작업 폴더 전체를 업로드했다면 빌드 소스에 포함됐을 가능성을 배제할 수 없다. 현재 앱은 Client Credentials 토큰 발급과 `read_orders` 권한 확인에 성공했지만, 배포 후 Shopify 관리 화면에서 Client Secret을 교체하고 Vercel의 `SHOPIFY_CLIENT_SECRET`도 같은 값으로 갱신해야 한다. 교체 전까지는 해당 비밀이 노출됐을 가능성이 남는다.

2026-08-03 Supabase 보안 점검이 `public` 스키마 전체 테이블에 RLS가 꺼져 있고 민감정보 열이 API로 접근 가능하다고 통보했다. 노출 대상에는 `users.password`(비밀번호 해시), `ebay_accounts`의 암호화된 OAuth 토큰, `orders`의 구매자 이름·계정·국가가 포함된다. 확인한 사실: 이 앱은 Supabase를 순수 PostgreSQL로만 쓰고(`src/lib/database-url.ts`) `supabase-js`·Auth·Storage·REST를 전혀 호출하지 않으며, 빌드된 클라이언트 번들(`.next/static`)에 Supabase 키가 들어 있지 않다. 따라서 공격에는 프로젝트의 anon 키가 필요하고 이 앱이 그 키를 공개한 적은 없지만, anon 키는 원래 공개를 전제로 발급되는 값이므로 유출 시 전체 데이터 읽기·수정·삭제가 가능하다. 조치 SQL은 `prisma/migrations/20260805000000_lock_down_data_api/migration.sql`에 있고 아직 운영에 적용하지 않았다. 근본 차단은 Supabase 프로젝트 설정에서 Data API의 노출 스키마에서 `public`을 제거하는 것이다. 적용 전에 `public` 테이블 소유자가 앱 연결 역할과 같은지 확인해야 한다(다르면 RLS 적용 후 앱이 모든 행을 읽지 못한다).
