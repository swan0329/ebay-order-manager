## 고정 토큰으로 열려 있던 관리자 진단 엔드포인트 (조치함, 후속 확인 필요)

`/api/admin/migrate-shopify`가 세션 검사 없이 소스에 하드코딩된 고정 문자열 하나만으로 열려 있었다. 2026-08-05 운영에서 재현을 확인했다(토큰 없이 `403`, 토큰 포함 시 `404` = 인증을 통과해 데이터베이스 조회까지 도달). 이 경로는 `?check=shopify`로 Shopify 관리자 토큰의 앞 6자와 길이, `?sku=`·`?preview=`로 내부 상품 데이터와 Shopify 관리자 URL을 로그인 없이 반환했다. 라우트를 삭제했고, 이 파일은 git에 커밋된 적이 없어 공개 저장소에는 노출되지 않았다(`git log -S`로 확인). 남은 확인: 이 엔드포인트가 열려 있던 기간의 접근 기록을 Vercel 로그에서 조회하고, 노출 정도를 감안해 Shopify 관리자 토큰 교체 여부를 결정한다. 나머지 15개 `/api/admin/*` 라우트는 모두 `requireApiUser()`를 쓴다.

## Supabase Data API로 전체 테이블 노출

2026-08-03 Supabase 보안 점검이 `public` 스키마 전체 테이블에 RLS가 꺼져 있고 민감정보 열이 API로 접근 가능하다고 통보했다. 노출 대상에는 `users.password`(비밀번호 해시), `ebay_accounts`의 암호화된 OAuth 토큰, `orders`의 구매자 이름·계정·국가가 포함된다. 확인한 사실: 이 앱은 Supabase를 순수 PostgreSQL로만 쓰고(`src/lib/database-url.ts`) `supabase-js`·Auth·Storage·REST를 전혀 호출하지 않으며, 빌드된 클라이언트 번들(`.next/static`)에 Supabase 키가 들어 있지 않다. 따라서 공격에는 프로젝트의 anon 키가 필요하고 이 앱이 그 키를 공개한 적은 없지만, anon 키는 원래 공개를 전제로 발급되는 값이므로 유출 시 전체 데이터 읽기·수정·삭제가 가능하다. 조치 SQL은 `prisma/migrations/20260805000000_lock_down_data_api/migration.sql`에 있고 아직 운영에 적용하지 않았다. 근본 차단은 Supabase 프로젝트 설정에서 Data API의 노출 스키마에서 `public`을 제거하는 것이다. 적용 전에 `public` 테이블 소유자가 앱 연결 역할과 같은지 확인해야 한다(다르면 RLS 적용 후 앱이 모든 행을 읽지 못한다).

## 워터마크 제거 품질

포카마켓 이미지에 워터마크가 있는 조건에서 제거 흔적이나 카드 무늬 훼손이 발생한다. 승인 가능한 판매 이미지를 안정적으로 만들지 못해 이미지 업무의 처리량과 품질에 직접 영향을 준다. 워터마크 잔상·카드 고유 무늬 훼손·카드 테두리 손상을 각각 주입한 합성 고정 회귀 테스트와 사람 승인 전 상품 이미지 불변 테스트는 추가됐다. 실제 운영 반려 이미지의 원본·처리 결과·사람 승인 정답을 익명 고정 세트로 확보하고 제거 방식별 결과를 사람 평가와 함께 비교하는 작업은 남아 있다.

## 포카마켓 최신 정보 수집 방식

공개적으로 확인되는 공식 개발용 API가 없어 상품·가격·판매 상태를 안정적으로 최신화할 계약이 없다. 화면 자동화는 변경에 약하고, 통신 분석은 이용 조건과 계정 보안을 확인해야 한다. 외부 제공 여부를 이 작업에서 확정할 수 없었다. 포카마켓에 제휴·내보내기 수단을 문의하고, 없다면 본인 기기의 정상 통신에서 최소 필드만 추출하는 검증용 연결을 설계한다.

## 런타임 데이터 구조 변경

AI 이미지와 포카마켓 구매 등 일부 기능은 요청 처리 중 테이블이나 인덱스를 만든다. 동시에 요청되거나 배포 권한이 제한되면 기능이 실패할 수 있고 데이터 구조의 실제 버전을 추적하기 어렵다. 광범위한 미커밋 작업과 운영 데이터 호환성 때문에 지금 즉시 제거할 수 없다. 모든 런타임 SQL을 목록화하고 데이터 보존 마이그레이션으로 옮겨야 한다.

로컬 데이터베이스는 실제 테이블 일부가 런타임·수동 방식으로 추가된 반면 `_prisma_migrations`에는 2026년 5월 이후 다수 마이그레이션이 미적용으로 남아 있었다. 2026-08-13에 전체 백업과 복제 DB 적용 검증 후 33개 마이그레이션을 모두 적용했고 상품 9,765건과 총 재고 50,853개가 보존됨을 확인했다. 다만 배포 데이터베이스는 별도이므로 배포 전에 같은 백업·복제 검증 절차를 반복해야 한다.

로컬 상품 9,765건은 모두 `image_source='pocamarket'`이고 촬영본 연결 또는 AI 승인 완료 상품이 0건이다. 따라서 실제 옵션상품 후보와 eBay용 Add CSV 검증은 이미지 완료 데이터가 있는 배포 데이터베이스에서 수행해야 한다. 로컬 원본 이미지를 완료 이미지로 임의 승격하면 안 된다.

## 손상된 한글

기존 README와 여러 소스 메시지에서 한글이 깨져 있다. 사용자 화면과 오류 진단의 의미가 훼손될 수 있다. 원래 문구를 코드만으로 확정할 수 없어 일괄 복원하지 않았다. 실제 화면과 업무 의미를 기준으로 파일별 복원 및 UTF-8 검증이 필요하다.

## 운영 복구 정책

데이터 보존 기간, 정기 백업, 복구 시험 절차가 정해지지 않았다. 주문·재고·구매 기록이 손상되면 사업 운영을 복구할 기준이 없다. 운영 책임자의 정책 결정이 필요하므로 이번 작업에서 임의로 정하지 않았다.

## 환경설정 예제 누락

`.env.example`을 복사한 조건에서 Shopify, 포카마켓 Android 연결, 로컬 AI, Cloudflare 관리 작업에 필요한 여러 변수가 빠져 있다. 선택 기능을 켜는 개발자와 운영자가 실행 중 오류가 난 뒤에야 누락을 알게 된다. 이번 작업은 문서만 정리하며 기존 코드·설정 파일을 변경하지 않는 범위라 예제 파일을 수정하지 않았다. 각 기능의 필수·선택 값을 실제 운영 환경과 대조한 뒤 비밀값이 없는 설명용 항목을 `.env.example`에 추가해야 한다.

## eBay 활성상품 보고서 연속 재요청 실패

2026-08-27 15:45 KST 전체 활성상품 보고서는 정상 완료됐지만, 바로 뒤 수량 3건을 수정한 후 최종 보고서를 두 차례 다시 요청했을 때 모두 `eBay Inventory API request failed.`로 거절됐다. 기존 전체 보고서는 보존됐고 세 상품의 수량 변경은 `ReviseInventoryStatus` 후 `GetItem` 재조회로 실제 반영을 확인했으므로 판매 상태에는 영향이 없다. 다만 보고서 화면은 다음 정상 수집 전까지 세 상품의 수정 전 수량을 보여줄 수 있다. 30분 주기 자동 수집의 다음 성공 여부를 확인하고, 반복되면 Inventory API 응답 코드와 요청 제한 정보를 안전 로그에 추가해야 한다.
